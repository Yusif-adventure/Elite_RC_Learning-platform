## What is already in place

### Backend (`backend/server.js`)

| Need | Where |
| --- | --- |
| Load the final exam without its answer key | `GET /api/courses/:courseId/final-exam` returns `passMark`. Members get 404 for draft courses. |
| Submit an attempt | `POST /api/quizzes/:quizId/attempts` returns `{ attempt, attemptsRemaining, passed, certificate, review }` |
| Three attempts, and no attempt after a pass | Enforced in the POST, which answers 409 with a message |
| Course completion and one certificate | `completeCourse()` runs when a final exam is passed. `certificates` is unique on `(user_id, course_id)`, and `certificate_identifier` is generated by the database. |
| A failed submission does not use up an attempt | If the certificate step fails, the attempt and completion are deleted and the member gets a 500 response |
| Attempt history on any device | `GET /api/quizzes/:quizId/attempts?review=latest` returns `{ attempts, attemptsRemaining, review }`. `attemptsRemaining` is set for final exams. |
| Staff verification | `GET /api/staff/certificates/:identifier` |
| Rules | 50 questions per final exam, 80% default pass mark (`DEFAULT_PASS_MARK`), and `FINAL_EXAM_ATTEMPTS = 3` |

### Frontend (`frontend/features/quiz/`)

- `quizApi.ts`: `submitAttempt` and `loadAttemptHistory` work for final exams
  unchanged. Add a `loadFinalExam(courseId)` next to `loadLessonQuiz`, which
  returns null on 404.
- `quizState.ts`: the types already include `attemptsRemaining`, `passed` and
  `Attempt.passed`. Every helper there works for any quiz.
- `LessonQuiz.tsx`: the questions form and the review list are written inline
  in this component. To reuse them, move them into `QuizQuestions` and
  `QuizReview` components that take the quiz, the answers and the review.
  A `FinalExam` component can then add the pass mark, the pass/fail result,
  attempts remaining, and the closed state. The class names all start with
  `lesson-quiz-`. Reuse them rather than the builder's `quiz-*` classes in
  `features/staff/courseBuilder.css`, which load globally and would clash.
- Styling rules followed so far:
  - use the tokens in `index.css` (`--navy`, `--blue`, `--sky`, `--line`,
    `--green`, `--red`, `--muted`)
  - full 1px borders, never coloured one-sided borders
  - right and wrong always shown with an icon and words, not colour alone
  - touch targets at least 44px tall
  - one column at 760px and below

## Day 5 work

1. **Decide what "completed the required course content" means.** This is not
   decided yet. The simplest rule is that every lesson in the course is marked
   complete in `lesson_progress`. Progress lives in the browser-readable
   `lesson_progress` table, keyed by `[section, title]`, so the backend has to
   read it with the service role and match keys. Whether lesson quizzes must
   also be attempted is a product decision. Ask before choosing.
2. **Enforce it on the backend.** The final-exam GET and the attempt POST
   should refuse with 403 and a clear message until the requirement is met.
   Staff can skip the check.
3. **Final exam page.** Add a route such as `/courses/:id/final-exam` in
   `routes.ts`, with a link from the course page and from the last lesson. It
   should show:
   - the locked state with what is left to finish
   - pass mark, questions, and attempts used out of 3
   - the result with pass or fail and attempts remaining
   - the passed or all-attempts-used state, with no further attempts
4. **Certificate.** Members need to view and download their certificate (with
   course title, member name, issue date and identifier), and staff need a
   verification lookup. The backend already issues the certificate, so these
   are the remaining pieces:
   - a member endpoint to read their certificates (or RLS reads, since 004
     lets members select their own rows)
   - a printable page; a print stylesheet is enough for "download as PDF"
   - a staff verify screen that uses the existing endpoint
5. **Make the attempt and the certificate one transaction.** Today a failure
   is undone by deleting the rows afterwards. A Postgres function called
   through `supabaseAdmin.rpc` would make it atomic. Nice to have, not a
   blocker.

## Known gaps

- Lesson progress is still keyed by `[section, title]`, so renaming a lesson
  resets its progress. Lesson quizzes do survive renames, because the builder
  sends the quiz back with its id.
- The in-memory Supabase in `backend/test/fakeSupabase.js` ignores `order`,
  and its timestamps start in 1970. Sort in code, as
  `GET /api/quizzes/:id/attempts` does, and do not test real dates against it.
- Run the quiz flow once against a real Supabase project with 004 to 006
  applied. Locally it was only checked against the in-memory Supabase.
